# 專案討論紀錄

## 起點：問題是什麼

長年讀《經濟學人》，喜歡它的視角，但受不了它「每件事騷個癢就沒了」的格式，也討厭被演算法推著走。想自己掌握一份閱讀清單。

最初想的是「找一份新的刊物來訂」，但真正的需求逐漸收斂成：

> 我提供一份想監測的來源清單（不管有沒有訂閱），每天早上打開電腦能看到「昨天新增」的內容，按來源彙整，每筆有標題、網址、一句中英對照摘要，形式是網頁（點了還在瀏覽器裡）。

也就是要自己搭一個**反演算法的閱讀聚合器**，而不是換一家媒體。

---

## 一個貫穿全程的前提：聚合 ≠ 繞過付費牆

清單裡很多來源（經濟學人、Foreign Affairs…）有付費牆。明確劃線：**不破解、不繞過付費牆**。

關鍵洞察讓這件事變簡單：使用者要的「標題 + 網址 + 一句摘要」這三樣，**幾乎都在各家公開 RSS 的 metadata 裡**（那是出版方自己發佈的 feed 摘要），連沒訂閱也讀得到。所以我們只聚合 metadata、全文連回原站讀——這跟任何 RSS 閱讀器做的事一樣，正當且禮貌。

這個前提決定了整個架構：我們是「昨日新內容的目錄」，不是內容的轉載者。

---

## 設計方向的演進

### 第一層：用什麼當「中樞」
RSS 閱讀器是「反演算法」最對症的工具——純時間序、來源自選、無推薦。

來源依付費牆狀況分三桶處理：
- **A 桶 — Substack/電子報**（清單裡最大一塊）：RSS + email 原生，付費後還有全文私人 feed。
- **B 桶 — 有 RSS 但內文付費**（經濟學人、LRB…）：RSS 給標題+摘要，知道新增了什麼，全文點回原站。
- **C 桶 — 本來就免費**（Rest of World、Semafor…）：直接吃。

### 第二層：自己搭 vs 買現成
| 方案 | 好處 | 壞處 |
|---|---|---|
| **買 Readwise Reader** ($8/月) | 零維護、一個 app 吃 RSS+email+付費 Substack、有「昨日新增」視圖 | 要付月費；客製化空間小；不是「自己的東西」 |
| **自己 self-host** | 完全掌控、可客製（中英摘要、AI 排序）、幾乎免費 | 要自己搭、自己顧 |

使用者選了自己搭（人在 playground，想做這個）。

---

## Host 方式：三條路的取捨

| 路線 | 好處 | 壞處 | 結論 |
|---|---|---|---|
| **A. 全跑在本機 Mac**（launchd） | 零成本、馬上能做 | Mac 沒開機就不更新、只在這台看 | 起手太受限 |
| **B. GitHub Actions + Pages** | 全免費、不靠電腦開機、手機電腦都能開同一網址、自動有 git 存檔、近零維護 | 要 GitHub 帳號 + 一把 Claude API key | ✅ **採用** |
| **C. 一台小 VPS** | 最自由（可跑 RSSHub、可做需登入的進階抓取） | 要顧機器、每月幾美金 | 現在用不到，未來要抓「無 feed 且需登入」的站再考慮 |

選 B：它正好命中全部需求——使用者提供清單 → 每天自動監測 → 中英摘要 → 一個網頁 → 不靠電腦、無演算法、完全掌控。

---

## 摘要怎麼產：四個選項

| 選項 | 好處 | 壞處 |
|---|---|---|
| **Claude 重寫英文摘要 + 翻中文**（採用） | 品質一致、中英都有 | 要花 token（但極低） |
| 用 feed 原摘要當英文、只翻中文 | 更省 | 英文摘要長短不一、品質參差 |
| 不做摘要、只列標題+連結 | 最快、零成本 | 解渴程度低 |

選了 Claude 重寫＋翻譯。並做了降級設計：**沒有 API key 時自動退回「feed 原摘要、不翻譯」**，所以不會因 key 問題整個掛掉。

---

## 一個關鍵的觀念釐清：訂閱 ≠ API

使用者有 Claude.ai 的 Max 訂閱，問能不能拿來當 API key。釐清：

- **Claude.ai 訂閱**（claude.ai 月費）和 **Anthropic API**（console 按 token 計費）是**兩個產品、兩套帳**。訂閱**不給** API key。
- Claude Code/Agent SDK 確實能用訂閱 OAuth 跑——但那適合「本機、你親自跑」。
- 我們是 **GitHub Actions 無人值守 cron**，OAuth token 短效、env var 帶進去不自動續期，**headless 環境該用 API key（機器身分）**。

結論：去 console.anthropic.com 申一把 API key（與訂閱分開），月費估計幾毛~一美金。使用者照辦並完成。

## 部署時的兩個現場決定

1. **Secret 放哪**：用 **Repository secret**（整個 repo 可讀、最穩），而非 Environment secret（要剛好建在 `github-pages` 環境下才生效，給多環境/審核關卡用的，這專案用不到）。

2. **Private repo 撞到 Pages 限制**：免費方案的 Pages 只支援 public repo。釐清「就算付費讓 private repo 發 Pages，網站本身仍是公開的（只有 Enterprise 能鎖站）」，所以保持 private 只保護原始碼、不保護 digest 網頁。權衡後**選擇把 repo 改 public**：key 在 Secrets 不外洩，公開的只有程式碼和公開文章 metadata，敏感度低。改 public 前先移除了個人對話紀錄檔。

---

## 最終決定（一句話）

**一個 Python 腳本，由 GitHub Actions 每天早上排程執行：抓各家公開 RSS → 跟 seen 記錄比對挑出新文 → 用 Claude Haiku 產生中英摘要 → 輸出靜態 HTML → 部署到 GitHub Pages。免費、自動、無演算法、來源完全自選。**
