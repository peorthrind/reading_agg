📺 什麼是循環工程（Loop Engineering）？程式員與 AI 協作模式的下一個階段
Best Partners TV · 19 分鐘
「循環工程」是用自動化系統替代人工逐步提示 Coding Agent，讓 AI 在無人值守的情況下持續驅動自身運轉，而工程師的核心工作從「寫提示詞」轉變為「設計這套循環系統」。
  • **概念由來與行業共識**：OpenClaw 開發者 Peter Steinberger 提出「不應再手動提示 Agent，而應設計讓 Agent 自動運行的循環」；Claude Code 負責人 Boris Cherny 也公開表示自己已不再手動提示 Claude，而是有「很多後台循環負責提示 Claude 並判斷下一步」；Andrej Karpathy 的 AutoResearch 同樣以「把人從循環裡抽離、提升 token 吞吐量」為核心目標。
  • **五大核心模組**：① 自動化（Automations）——定時觸發任務，結果主動回饋，例如每天自動分類 issue、匯總 CI 失敗；② 工作樹（Worktrees）——為每個 Agent 建立獨立的 Git 分支工作目錄，從根源避免多 Agent 並行時的檔案衝突；③ 技能（Skills）——把專案規則、規範、踩坑紀錄寫成可複用的文件，解決每次新會話都要重新說明背景的「意圖債務（Intent Debt）」問題；④ 插件與連接器（Plugins & Connectors）——透過 MCP 協議接入 Jira、資料庫、CI、即時通訊等外部工具，讓循環能自動建立 PR、更新工單、發送通知；⑤ 子 Agent（Sub-agents）——把「寫程式的 Agent」和「驗證程式的 Agent」拆分，避免模型自我評審寬鬆的問題，/goal 指令底層也用了同樣的生成與校驗分離邏輯。
  • **記憶系統是長期運行的基礎**：大模型每次運行之間不保留記憶，因此必須有外部持久化儲存（Markdown 檔案、專案看板、狀態文件）記錄哪些已完成、哪些待處理，讓隔天的自動化任務能從上次停下的地方繼續，而非每次從頭開始。
  • **三大不會消失的人類責任**：① 驗證責任——「循環說完成」只是聲明，不是驗證結論，最終仍需人工確認代碼可正常運行；② 理解債（Comprehension Debt）——循環產出速度越快，工程師沒有親手寫過的代碼累積越多，對代碼庫的理解會持續退化，唯一解法是認真閱讀每一份循環生成的代碼；③ 認知投降風險——當循環能自動運行，人最容易直接接受所有結果、停止主動判斷，循環可以是提升效率的解藥，也可以是加速能力退化的加速劑，取決於使用者的態度。
  • **工具現狀**：Claude Code 與 OpenAI Codex 都已原生支援上述五個模組，底層架構高度一致，為一款工具設計的循環邏輯通常可直接移植到另一款；但整體仍處極早期，最現實的挑戰是 token 成本控制與無人值守時代碼品質下滑的問題。

**背景與核心人物**

過去兩年，工程師與 Coding Agent 的協作模式是「人寫提示詞 → AI 輸出 → 人再輸入下一步指令」，Agent 更像一個需要全程握持的工具。現在業界開始出現轉變：OpenClaw 開發者 Peter Steinberger 明確提出「不應再手動提示 Coding Agent，而應設計讓 Agent 自動運行的循環」；Claude Code 負責人 Boris Cherny 表示自己已不再手動提示 Claude，而是由後台的多個循環負責提示 Claude 並決定下一步，自己的工作就是編寫這些循環；Andrej Karpathy 的 AutoResearch 也以「把人從循環裡抽離、最大化 token 吞吐量」為核心思路。

**什麼是循環工程**

循環工程的本質，是用你設計的系統替代你自己去完成對 Agent 的提示與調度。你只需定義最終目標，AI 反覆迭代執行直到目標完成，整個過程不需要人逐步觸發。這個概念位於「Agent Harness Engineering（單 Agent 運行框架）」的上一層，相當於一個跑在計時器上、能自主生成子 Agent 並自我驅動持續運轉的系統。

**五大核心模組**

第一，**自動化（Automations）**：設定任務週期，讓系統定時自動觸發，有結果主動回饋，無問題則自動歸檔。Codex 和 Claude Code 都支援，實際用例包括每天自動分類新 issue、匯總 CI 失敗記錄、排查上週新引入的 bug。進階指令 /goal 可讓 Agent 持續運行直到可驗證的停止條件成立（如「認證模組所有測試通過且格式檢查無誤」），由獨立的小模型判斷是否完成，而非執行任務的 Agent 自評。

第二，**工作樹（Worktrees）**：多 Agent 並行時最大問題是檔案衝突。Git 工作樹為每個 Agent 建立獨立工作目錄和分支，共享倉庫歷史但物理隔離修改，從根源避免衝突。但要注意「編排稅」：工具能提升執行端效率，審核與判斷的工作量最終仍落在人身上，你一天能認真審核多少產出才是真正的上限。

第三，**技能（Skills）**：解決每次新會話都要重新說明專案背景的「意圖債務（Intent Debt）」。Skills 把專案規則、規範、構建步驟、踩坑紀錄正式記錄成文件，Agent 每次運行都能讀取，知識可不斷積累產生複利效應。Plugins 則是 Skills 的分發機制，可打包多個 Skill 和 Connector 供團隊一次安裝即用。

第四，**插件與連接器（Plugins & Connectors）**：透過 MCP 協議把 Agent 接入外部工具（需求追蹤器、資料庫、測試環境 API、即時通訊等），讓循環能自動建立合併請求、關聯工單、通知相關人員。這是普通 Agent 和完整循環的核心差異：普通 Agent 只給建議，完整循環能直接執行端到端的工作流。

第五，**子 Agent（Sub-agents）**：把「寫程式」和「驗證程式」的角色拆給不同的 Agent，甚至可以使用不同的模型和推理強度（如安全審查 Agent 用能力更強的模型開高推理，探索型 Agent 用輕量快速模型開只讀權限）。這個分離設計在無人值守的循環裡尤為重要，因為你需要一個值得信賴的驗證環節才能放心讓循環自主運行。

**記憶系統**

大模型每次運行之間不保留記憶，因此必須依賴外部持久化儲存（Markdown 文件、專案看板、狀態文件）。狀態文件記錄哪些方案試過、哪些驗證通過、哪些還在處理，讓隔天的自動化任務從上次停下的地方繼續，而非每次從頭開始。

**人類責任不會消失**

循環不會把人剔除出工作，反而有三個問題會隨循環能力增強而更突出：① **驗證責任**：「循環說完成」只是聲明，最終仍需人工確認代碼正常運行；② **理解債（Comprehension Debt）**：循環產出越快，工程師沒有親手寫過的代碼累積越多，對代碼庫的理解持續退化，唯一解法是認真閱讀每份循環生成的代碼；③ **認知投降風險**：循環自動運行時，人最容易停止主動判斷、直接接受所有結果——循環可以是效率解藥，也可以是能力退化的加速劑，兩者取決於使用者是否保持判斷力。

**結論**

Boris Cherny 的觀點不是說程式員的工作變簡單了，而是說工作的槓桿點轉移了：以前的槓桿來自寫好提示詞，現在的槓桿來自設計一套能持續運行的系統。設計循環比寫提示詞更難，而不是更簡單。你可以去搭建自己的循環，但要以工程師的身份去搭建，而不是做一個只會按下啟動鍵的人。

💡 值得讀：如果你正在用 Claude Code、Codex 或任何 Coding Agent，這支影片能幫你看清下一步的演進方向——從「怎麼寫好提示詞」升級到「怎麼設計一套能自動驅動 Agent 的系統」，並且清楚解釋了五個模組的具體運作與三個不會因自動化而消失的人類責任，避免你把循環工程當成「放手不管」的藉口。
📄 TimesFM 2.5：Google Research 開源時間序列基礎模型
Google-Research · 516 字
Google Research 推出的預訓練時間序列預測基礎模型 TimesFM，最新 2.5 版以更小參數量支援更長上下文與分位數預測。
  • TimesFM 2.5 參數量從 500M 縮減至 200M，但上下文長度從 2048 大幅提升至 16k，同時可選配 30M 的分位數頭，支援最長 1k 步的連續分位數預測。
  • 模型已移除原本需手動指定的 frequency 指標，並新增數個預測旗標（如 normalize_inputs、force_flip_invariance、infer_is_positive、fix_quantile_crossing），讓使用介面更簡潔且具彈性。
  • 2.5 版完成了多項工程改進：Flax 後端支援（加快推理速度）、透過 XReg 加回協變量（covariate）支援、整合 HuggingFace Transformers + PEFT（LoRA）的微調範例，以及核心層的單元測試。
  • 已在 Google 1P 產品中部署：BigQuery ML（SQL 查詢規模化）、Google Sheets（試算表直接使用）、Vertex Model Garden（容器化端點供 Agent 呼叫），並發布 SKILL.md 供 AI Agent 使用。
  • 安裝彈性高，支援 torch 與 flax 兩種後端，需要協變量時可額外安裝 xreg 套件，也提供 uv 虛擬環境的快速建置流程。

**模型定位與論文** TimesFM（Time Series Foundation Model）是 Google Research 開發的預訓練時間序列預測基礎模型，對應 ICML 2024 論文《A decoder-only foundation model for time-series forecasting》，採用純解碼器架構。模型權重發布於 Hugging Face，並非官方支援的 Google 產品。

**TimesFM 2.5 核心升級** 與前一代 2.0 相比，2.5 版做了大幅調整：參數從 500M 降至 200M（更輕量），但上下文視窗從 2048 躍升至 16k（大幅提升長序列能力）；另可選配 30M 的連續分位數頭，支援最長 1000 步的不確定性預測，輸出包含均值與第 10 至 90 百分位。頻率指標（frequency indicator）被移除，降低使用門檻，並新增多個預測旗標（normalize_inputs、force_flip_invariance、infer_is_positive、fix_quantile_crossing）讓使用者精細控制推理行為。

**已完成的工程里程碑** 自 2025 年 9 月發布以來，陸續完成：Flax 版本支援更快推理、透過 XReg 重新引入協變量（covariate）支援、完整文件與範例、LoRA 微調範例（HuggingFace PEFT）、核心層單元測試，以及 SKILL.md 供 AI Agent 框架呼叫。

**產品整合與使用方式** 模型已整合進 BigQuery ML、Google Sheets 與 Vertex Model Garden。安裝上可選 torch 或 flax 後端（`pip install timesfm[torch]` 或 `timesfm[flax]`），需要協變量時加裝 `timesfm[xreg]`。使用流程極簡：載入預訓練模型、設定 ForecastConfig、呼叫 `model.forecast()` 傳入多條時間序列，即可同時取得點預測（shape: batch × horizon）與分位數預測（shape: batch × horizon × 10）。

💡 值得讀：若你需要在實際專案中部署或評估時間序列預測模型，此頁完整說明了 TimesFM 2.5 的能力邊界、安裝方式與快速上手範例，能幫你在幾分鐘內判斷它是否適合你的使用情境。
📄 PP-OCRv6 正式開源：精度、速度、場景全面代際躍升，瀏覽器端單圖僅 97ms
魔搭Modelscope社区 · 1909 字
百度飛槳 PaddleOCR 發布第六代 OCR 模型 PP-OCRv6，首次推出三檔模型（Tiny/Small/Medium），精度提升 5%、速度提升 5 倍，支援 50 種語言，可一鍵替換 v5。
  • 三檔模型覆蓋全算力平台：Tiny（1.5M）專為瀏覽器/極端邊緣設備，Small（7.7M）針對手機/嵌入式，Medium（34.5M）對應伺服器；模型體積小但性能大幅超越前代同級。
  • 精度跨代提升：文字檢測精度較 PP-OCRv5 同級模型提升 4.9%，文字識別精度提升 5.1%，並在自建多場景評估集上斷層領先通用大模型。
  • 推理速度暴增：Medium 在 Intel Xeon 8350C CPU（搭配 OpenVINO）端到端延遲僅 1.40s，是前代 PP-OCRv5_Server 的 5.2 倍速；Tiny 在 M4 芯片本地瀏覽器環境下單張圖片僅需 97ms。
  • 場景與語言大幅擴充：單模型支援語言從 PP-OCRv5 的 4 種擴展至 50 種；新增電路板、數碼管、CAD 圖紙、噴碼點陣字符等工業場景。
  • 魯棒性歷史最高：多尺寸預測一致性方差僅 5.19%（較 v5 降低 35%）；邊緣尺寸擾動評估集上識別一致性提升 20.5%。
  • 可無縫平替 v5：架構與 API 相容，支援 onnxruntime、transformers 多後端，PaddleOCR 3.7.0 起預設模型已切換至 v6，絕大多數現有管線可直接升級。

百度飛槳 PaddleOCR 團隊正式開源 PP-OCRv6，即 PP-OCR 系列第六代文本檢測識別模型，並配套發布 PaddleOCR 3.7.0。

**三檔模型設計** PP-OCRv6 首次推出三個規格：Tiny（1.5M）、Small（7.7M）、Medium（34.5M），分別對應瀏覽器/極端邊緣設備、手機/嵌入式設備、伺服器三種算力場景，開箱即用。與前代對應關係為：Medium 對標 v5_Server 但精度反超、Small 對標 v5_Mobile、Tiny 無前代直接對標。

**精度與速度** 文字檢測精度較 PP-OCRv5 同級模型提升 4.9%，識別精度提升 5.1%，研究團隊強調這是「代際提升」而非微調級漲點，在自建多場景評估集上同時斷層領先通用大模型。推理速度方面，Medium 在 Intel Xeon 8350C + OpenVINO 環境下端到端延遲 1.40s，達到 v5_Server 的 5.2 倍速；Tiny 在 M4 本地瀏覽器環境下單圖僅 97ms。

**場景與語言擴充** 單模型支援語言從 4 種躍升至 50 種。工業場景方面新增電路板、數碼管、CAD 圖紙、噴碼點陣字符等複雜場景的檢測與識別能力。

**魯棒性提升** 多尺寸預測一致性方差僅 5.19%（較 v5 降 35%）；邊緣尺寸擾動識別一致性較 v5 提升 20.5%，整體穩定性為歷代最高。

**使用與遷移** PaddleOCR 3.7.0 起預設模型已切換為 v6；支援 onnxruntime、transformers 多推理後端，可透過 `--engine` 參數指定。PP-OCRv6 嚴格規避複雜非通用算子，現有 v5 管線可無縫平替升級。PP-OCR 系列自 2020 年 v1 發布至今，已成為 UmiOCR、MinerU、TurboOCR 等工具鏈的底層 OCR 引擎。
